# Tauri packaging proof of concept

This build-time Rust tool reads **deka.json**, compiles its DekaScript entry to VM
bytecode, and calls the real `tauri-bundler` 2.9.4 library to create a macOS `.app`.
There is no `tauri.conf.json`, Tauri application runtime, WebView, JavaScript or V8.
The compiler and bundler stay in the build tool, outside the shipped application.

The schema is experimental and currently consumed only by this tool, not the
production `deka build` command. The demo supports macOS app bundles only. It
always skips Tauri credential-based signing, then applies an explicit local
ad-hoc signature. It does not notarize or publish anything.

## Build and package

From the repository root, with the normal repository build directories:

```sh
export CARGO_TARGET_DIR="$PWD/.target" TMPDIR="$PWD/.tmp"
cargo build --locked --profile native --manifest-path crates/deka_vm/Cargo.toml --no-default-features --features gpu --bin dvm-ui
cargo build --locked --release --manifest-path tools/deka-package/Cargo.toml
.target/release/dvm-package crates/deka_vm/examples/packaged-counter/deka.json .target/native/dvm-ui --out .tmp/packaged-counter
open '.tmp/packaged-counter/bundle/macos/Deka VM Counter.app'
```

`deka.json` owns the package name/version and a `desktop` section containing
`productName`, `identifier`, `entry`, `entryFunction`, `description`, `icons` and
`resources` (source-to-destination map). Entry, icon and resource source paths are
relative to that manifest, independent of the shell's current directory. Resource
destinations are relative to the bundle's Resources directory; `app.dvm.json` is
reserved for compiled application bytecode. The icon is copied from the existing
Deka website's 512px application icon, rather than inventing a new brand asset.

The `.app` contains:

```text
Contents/
  Info.plist                 # Generated by Tauri from deka.json
  MacOS/deka-app             # VM + native renderer, no compiler
  Resources/app.dvm.json     # Compiled application
  Resources/<app name>.icns  # Converted by Tauri from the configured PNG
  Resources/ABOUT.txt        # Configured sample resource
```

The entire `.app` is movable. Launching it requires neither the source checkout
nor a system Deka/Rust installation. The runtime resolves its payload relative
to its executable, never the current working directory. The demo still uses
the renderer's existing generic window title; package/Dock identity comes from
the configured app metadata. No update service or public signing pipeline is
included. This host build does not establish compatibility with other OSes or
architectures; release deployment targets must also match compiled dependencies.

## Verify the artifact

```sh
python3 tools/deka-package/test_bundle.py .target/release/dvm-package .target/native/dvm-ui crates/deka_vm/examples/packaged-counter/deka.json .tmp/package-tests
```

This changes both source and configuration, packages the result, moves the `.app`,
deletes its source/staging directories, then runs its real VM click handlers. It
checks generated metadata, icon, resource bytes and signature. Removing the
bundled bytecode must produce a failure instead of falling back to source files.

On the Intel macOS 26.7 development host, the complete locally signed counter
bundle contained 3,343,536 file bytes (3.19 MiB). It was copied to a separate demo
directory and opened through LaunchServices. `codesign --verify --strict` passed.
The artifact test also passed; using the previous runtime without bundle-relative
payload loading made the same test fail when invoking the relocated executable.
