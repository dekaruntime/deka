# Built-Artifact Manifest v2 and Artifact-Only Verification

Status: **spec — phase 1 of deka#743, implements RFD 54 (dekaruntime/rfd#54)**.
This document is the contract that deka#762 (build-time server entries), deka#763
(artifact-only loader), and deka#764 (end-to-end gate) build against. It specifies;
it does not implement. The machine-readable companion to §2 is
`crates/runtime_core/schemas/artifact-manifest-v2.schema.json` — together they are
the versioned schema of record for the `deka build` → `deka serve` / Worker adapter
boundary (see §6).

Written as a delta from the code on `main` (verified against `lane` @ `1f25b77a`),
not from first principles.

## 1. Layout

```
dist/
  build-manifest.json          the deployment descriptor (§2)
  build-manifest.sha256        the integrity anchor (§3)
  build-manifest.sig           optional detached signature over the same bytes (§3.3, reserved)
  server/                      every executable module. The resolution jail.
    app/**/*.js                page/layout/loading entries
    api/**/*.js                API handlers
    defer/**/*.js              server:defer entries
    .values/<slot-id>.js       materialized build values (ordinary modules)
    ds_modules/**              vendored dependencies the graph imports
  client/                      the static root
    index.html                 a build output (RFD 54 amendment 1)
    assets/**                  hashed assets, importmap
    **                         public files, prerendered HTML
  _worker.js                   Cloudflare adapter shim, generated FROM dist/server (§4.4)
```

Decisions, not options:

- **Everything executable lives under `dist/server/`.** `dist/app/`, `dist/src/`,
  `dist/api/` at the dist root are removed in #762. One root means one jail, and
  "resolved outside `server/`" is a single, checkable rule.
- **`dist/client/index.html` is a build output**, hashed and manifest-described
  like any other client payload. No consumer may treat a root `index.html` as
  evidence of anything. `ensure_web_project_layout` stops requiring it in source;
  when a source project has no `index.html`, `deka build` emits the default
  harness.
- **`dist/server/deka.json` / `deka.lock` stay** (the policy the artifact runs
  under travels with it) and are ordinary manifest payloads.
- `_worker.js` stays at the dist root because Cloudflare requires it there. It is
  a *shim*, declared in the manifest, and must be generated from `dist/server`.

## 2. `build-manifest.json` v2

JSON, UTF-8, `snake_case`, exactly one trailing `\n`. Deterministic: object keys in
the declared order below, every array sorted by its stated key. **Serialization is
pinned**: compact JSON (no incidental whitespace), struct field order as listed,
arrays pre-sorted before serialization — the same discipline v1's
`BuildManifest::canonical_json` already uses (`build_manifest.rs:698-713`). Two
builds of identical input produce byte-identical manifests; the `[rerun]`
determinism check (`build_fixture_harness.rs:726-728`) extends to cover this file
at its new location, and now compares `build-manifest.sha256` too.

```jsonc
{
  "format": "deka.artifact@2",
  "origin": "authored",              // "authored" | "materialized"  (§5.5)
  "producer": {
    "deka": "0.46.0",                // informational
    "dsc": "0.7.1",                  // informational
    "plan_version": 2
  },
  "compat": {
    "runtime_abi": 1,                // load-bearing; see §5.4
    "module_format": "esm2022",
    "targets": ["native", "worker"],
    "host_imports": ["deka:host/env", "deka:host/fetch"]   // the ONLY legal bare specifiers
  },
  "client": {
    "root": "client",
    "index": "client/index.html",    // omitted if the build emits no harness
    "trailing_slash": false
  },
  "server": {
    "root": "server",
    "entries": [
      {
        "id": "page:/posts/[slug]",
        "kind": "page",              // page | api | defer | not_found
        "module": "server/app/posts/[slug]/page.js",
        "export": "default",         // page/defer/not_found
        "methods": []                // api only, uppercase, sorted
      }
    ]
  },
  "worker": { "entry": "_worker.js" },   // present only when a worker shim was emitted
  "routes": [
    {
      "template": "/posts/[slug]",
      "mode": "static_params",       // static | static_params | request_time | api
      "instances": ["/posts/hello"], // static_params only, sorted
      "outputs": ["client/posts/hello/index.html"],  // static + static_params
      "entry": null,                 // required for request_time and api; null otherwise
      "slot": "abc123",
      "deferred": ["Reviews"],
      "source_file": "app/posts/[slug]/page.dsx"     // DIAGNOSTIC ONLY (§2.1)
    }
  ],
  "slots": [
    {
      "id": "abc123",
      "binding": "staticParams",
      "file": "app/posts/[slug]/page.dsx",           // diagnostic only
      "descriptor_digest": "sha256:…",
      "module": "server/.values/abc123.js",          // replaces v1's "deka:dev/abc123"
      "observations": []                              // dev-only; see §2.2
    }
  ],
  "payloads": [
    { "path": "client/index.html", "role": "client", "bytes": 1204, "digest": "sha256:…" },
    { "path": "server/app/page.js", "role": "server", "bytes": 8321, "digest": "sha256:…" }
  ],
  "payload_root": "sha256:…"          // §3.2
}
```

The normative shape, including which fields are required and the digest spelling,
is `crates/runtime_core/schemas/artifact-manifest-v2.schema.json`. The schema is
strict (`additionalProperties: false`); adding a field is a format-version bump,
which is what `format` exists for.

### 2.1 `source_file` is diagnostic only

It stays for error messages and the route table. **No consumer may resolve, read,
stat, or fall back to it.** A verifier that touches a source path has reintroduced
the bug. This is stated here and must be stated in the doc comment on the
deserializing struct; #763 gets a test that serves an artifact from a directory
where every source path in the manifest is nonexistent.

### 2.2 Fields that do not travel

`slots[].observations` (filesystem observations for `deka dev` invalidation,
deka#725) are dev metadata, not deployment facts. They are written only when
`origin == "materialized"` or into the dev cache copy; an authored `dist/`
manifest carries `observations: []`. Otherwise the deployment descriptor's bytes
change when an unrelated file is read at build time, and determinism degrades for
no consumer benefit. (The field is always present; it is `[]` in authored
manifests, so the schema does not branch on `origin`.)

### 2.3 Digest spelling

Every digest is `"<alg>:<lowercase-hex>"`, alg fixed at `sha256` for v2. v1's bare
hex is not accepted by a v2 reader. The prefix is what lets us add an algorithm
later without a v3.

### 2.4 `payloads` completeness

`payloads` lists **every regular file under `dist/` except `build-manifest.json`,
`build-manifest.sha256`, and `build-manifest.sig`** — the three files that
constitute the descriptor and its anchor. That includes the worker shim:
`_worker.js` is a payload with `role: "server"` **and** is named by
`worker.entry`; the two declarations must agree, and verification step §3.4.7
covers it once through its payload entry. Symlinks and non-regular files are a
build error (an artifact must survive a tar/zip round trip and a Worker upload).
Payload `path`s are forward-slash, `dist/`-relative, unique, and sorted; they lie
under `client/`, under `server/`, or are the root-level `_worker.js` — nothing
else lives at the dist root.

## 3. Integrity anchoring (RFD 54 invariant 7)

**Rule: no field inside the manifest ever contains a digest of the manifest.** The
chain runs outside-in.

### 3.1 The anchor

`dist/build-manifest.sha256` contains exactly one line:

```
<64 lowercase hex>  build-manifest.json\n
```

(i.e. the `sha256sum` text format: hex, two spaces, filename, newline.)

The digest is over **the whole `build-manifest.json` file as written on disk**,
byte for byte, trailing newline included. No canonicalization, no
re-serialization, no field exclusion — the hashed object is a file, not a data
structure. Consumers hash the bytes they read before parsing them.

Why a sidecar and not a self-hash-with-a-hole: computing a digest over "the
manifest minus this one field" makes the hashed object depend on a serializer's
field order and whitespace, which is precisely how a "verified" artifact ends up
verifying something other than what loads. A sidecar has one definition and one
implementation on both sides.

**What this does and does not buy.** An unsigned local anchor detects truncation,
partial writes, a half-copied deploy, an edited route table, a swapped module. It
does **not** resist an attacker with write access to `dist/` — they update the
sidecar. That is stated here rather than implied, because "we hash it" reads as
tamper-proof and is not.

### 3.2 `payload_root`

`payload_root` = `sha256` over the canonical payload table: for each entry of
`payloads` in path order, the exact bytes

```
<path>\0<digest>\n
```

concatenated, with paths forward-slash and `dist/`-relative. It is a single value
summarising the payload set, and it is *inside* the manifest — legal, because it
hashes the payload table, never the manifest.

It exists for the Worker adapter: workerd cannot walk a directory, so the adapter
embeds `payload_root` as a build-time constant and compares it against the
manifest it bundles. A mismatch means the bundle and the manifest came from
different builds. Native `serve` also uses it as the fast "did anything change"
check between an in-process cached verification and a re-verify.

### 3.3 Signing (reserved, not shipped in phase 1)

`dist/build-manifest.sig` is a detached signature over **the same bytes the
sidecar hashes** — the manifest file. Nothing else is ever signed, because the
manifest transitively covers every payload by digest, and the sidecar covers the
manifest. One chain: signature → manifest bytes → payload digests → payload
bytes.

Phase 1 ships digest-only verification and reserves the filename. See §7.1 for
the recorded decision and its follow-up condition.

### 3.4 Verification order

Strictly this order, all of it before a listener binds:

1. read `build-manifest.json` bytes
2. read `build-manifest.sha256`, recompute, compare
3. parse JSON (against the §2 shape; the JSON Schema is the normative statement of it)
4. check `format` and `compat` (§5.4)
5. recompute `payload_root` from the parsed table and compare
6. every `server.entries[].module`, `slots[].module`, and `worker.entry` is present in `payloads` and exists on disk
7. hash and compare **every `role: "server"` payload — which includes `worker.entry` — plus `client.index`**
8. bind the listener.

`role: "client"` payloads other than the index are verified **lazily, at first
read**, comparing the digest as the bytes are served. Rationale: a shop's client
root is thousands of images; hashing them all at boot converts every restart into
a cold-storage scan, while a static payload that is never requested is a payload
whose corruption never reached a user. Nothing is ever served unverified either
way. `deka verify` remains the eager full-tree check (`crates/cli/src/cli/verify.rs`,
retargeted at `dist/build-manifest.json`).

## 4. Portable server-module format

One emitted graph, two loaders (the native pool loader and the Worker adapter).
The rules are what make that possible.

1. **ES modules, ES2022, `.js`, UTF-8.** No CommonJS, no TypeScript, no
   `.ds`/`.dsx` under `dist/`. A `.ds` or `.dsx` file anywhere under `dist/` is a
   verification failure — the artifact must not carry compiler input.
2. **Every relative specifier is extension-explicit and resolves inside
   `dist/server/`.** No extensionless imports, no directory/`index.js` resolution,
   no `..` escaping the server root. This is a real change to the loader: the
   candidate-guessing in the `deka-modules` crate (`module_spec`) and
   `crates/pool/src/esm_loader/resolver.rs` is **disabled in artifact posture**,
   not merely unused.
3. **The only legal bare specifiers are the `compat.host_imports` allowlist**,
   namespaced `deka:host/*`. The native loader satisfies them with its host
   bindings; the Worker adapter satisfies them with an adapter shim exporting the
   identical surface. `deka:dev/*` is **not** in the allowlist and is rejected by
   name with a diagnostic saying it is a dev-only scheme.
4. **Build values are ordinary modules** at `server/.values/<id>.js`, imported
   relatively. No virtual scheme, no cache-first resolution, no
   `dist/app/.build-values` fallback. `build_values_dist.rs`'s specifier rewrite
   already does most of this; it moves to targeting `server/.values/`.
5. **Ambient globals are declared, not assumed.** `prepend_host_bindings`
   currently injects host globals into every module. In v2 the set is enumerated
   in `compat.host_imports`-adjacent form so the Worker adapter installs exactly
   the same names. An artifact that depends on an undeclared global is not
   portable, and nothing detects that today.
6. **Static import graph only.** `import()` is permitted with a string-literal
   specifier that resolves inside the server root; a computed dynamic import is a
   build error. A bundler must be able to trace the graph from the declared entry
   ids without executing it — that is the Worker adapter's whole requirement.
7. **Entry contract.** `kind: "page" | "defer" | "not_found"` → default export is
   the component. `kind: "api"` → named exports matching `methods`, each
   `(request) => Response | Promise<Response>`. A declared method with no
   matching export is a verification failure.

### 4.4 Worker adapter

`_worker.js` is generated **from `dist/server`** — it imports the declared entries
and the manifest's route table, and it embeds `payload_root`.
`write_worker_router_entry` + `transpile_bundle(project_root, …)` (source-rooted,
rescans `app/`) is retired in #763. Static assets come from the Worker's asset
binding over `dist/client`; nothing in the Worker path reads `.ds` or invokes dsc,
which is the property that made the edge target the forcing function for this
whole design.

## 5. Detection and verification

### 5.1 Resolving the subject

`deka serve <subject>` / `deka run <subject>`:

- `<subject>/build-manifest.json` exists → `<subject>` is the artifact root.
  (`deka serve dist/` — the unambiguous deploy form.)
- else `<subject>/dist/build-manifest.json` exists → `<subject>/dist` is the
  artifact root.
- else no artifact root.

`is_built_app_router_project`'s two file probes (`dist/client/index.html` +
`dist/app/page.js`) are replaced by "the manifest at the artifact root verifies".
File-existence probing cannot distinguish valid from tampered, and #760 put the
predicate in the right place precisely so its body could be replaced here.

`is_source_app_router_project` loses its root-`index.html` clause and becomes
`app/page.ds(x)` present (with `deka.json` at the root). Per RFD 54 invariant 8 it
answers only "can I develop this", and no code path may use it to answer "can I
serve this".

### 5.2 The four states

| State | Definition | Response |
|---|---|---|
| **absent** | No `build-manifest.json` at either candidate root **and** no `dist/` directory | Not an error. Materialize (RFD 54 §Materialization) or, for `deka dev`, use the source posture. |
| **incomplete** | `dist/` exists but has no `build-manifest.json`; or the manifest parses but a declared entry/payload is missing on disk; or the sidecar is missing | **Hard failure before bind.** |
| **tampered** | Sidecar digest mismatch; `payload_root` mismatch; any verified payload digest mismatch; a `.ds`/`.dsx` file under `dist/`; an unlisted file under `dist/server/` | **Hard failure before bind.** |
| **incompatible** | Unknown `format`; `compat.runtime_abi` this binary does not implement; `targets` does not include the target being served | **Hard failure before bind.** |

The distinction that matters: **`dist/` present with no manifest is `incomplete`,
not `absent`.** Otherwise "delete the manifest" becomes a supported way back to
the old silently-recompiling behaviour, and #743 comes back.

**Unlisted files.** Under `dist/server/` → failure: anything there is reachable by
the module resolver, so an unaccounted file is an unaccounted execution path.
Under `dist/client/` → warning, not failure: CDNs, `.well-known`, and deploy
tooling legitimately add files to a static root, and refusing to boot over a stray
`robots.txt` is a fault report nobody will trust.

### 5.3 Nothing binds early

Every check in §3.4 completes before the listener opens. No partial serving, no
"verify in the background", no serve-then-fail. The end-to-end gate in #764
asserts it by attempting a connection after a tamper and requiring
connection-refused, not a 500.

### 5.4 Compatibility

- `format` must equal `deka.artifact@2` exactly. Unknown → incompatible.
- `compat.runtime_abi` is an integer the serving binary must implement exactly
  (§7.2 records the bump policy). It changes only when the host-module contract
  changes (host imports, entry export shape, value module convention) — **not** on
  every deka release. `producer.deka` / `producer.dsc` are informational and
  never gate.
- `compat.targets` must contain the target being served (`native` for `deka
  serve`, `worker` for the adapter).
- Diagnostics name the fact, then the way out: `dist/ was built for runtime_abi 2;
  this deka implements 1. Rebuild with the matching toolchain: deka build`.

### 5.5 Authored vs materialized

Same schema, distinguished by `origin`. `authored` (in-project `dist/`) is never
regenerated implicitly; invalid means fail. `materialized` (content-addressed, in
the user-global cache from RFD 54 §Cache location) is runtime-owned; invalid means
*discard and re-materialize*, because staleness there is ordinary. The two must
not share a validity code path that assumes one behaviour — one function returns a
classified state, and the two callers decide what to do with it.

Cache keys include the compiler version, per RFD 54 invariant 5. `producer.dsc` in
a materialized manifest is a record of that, not the key itself.

## 6. The contract mechanism: versioned schema + fixture, not the seam system

#761's original brief required this boundary to be modeled in the seam-contract
system and `check_consumer`-ed before phase 3. **That requirement is withdrawn**
(Sami, deka#761 comment 2026-09-09): the seam system was built for inter-process
API boundaries (storefront, data_backend, harar_auth — request/response over a
wire), and `dist/build-manifest.json` is a versioned file with a producer and two
readers. That is a schema-and-fixture problem, not a wire-protocol one; reviving
three crates and a CLI to describe it is heavier machinery than the problem needs.

What replaces it:

- **A versioned schema.** `format: "deka.artifact@2"` carries the version; §2 is
  its statement in prose; `crates/runtime_core/schemas/artifact-manifest-v2.schema.json`
  is its machine-readable normative form. The schema is strict so producer drift
  fails loudly at the fixture, not subtly at a shop.
- **A fixture proving producer and consumer agree.** `deka build` writes a
  manifest, the loader reads it, and the test fails if either side drifts. That
  fixture is phase 3's (#763) deliverable — it cannot exist before the loader —
  and it is asserted in CI the day the loader lands.

The precedent is deka#751, not the seam system: deka's parser silently dropped
every `[transpile] `-prefixed diagnostic dsc emitted, producing 358 phantom
divergences. A shape fixture comparing dsc's actual output to deka's parser
expectations would have caught it. That is the pattern this copies: real bytes on
both sides, compared by a test.

The unused seam data model and contract generators were subsequently removed
during the runtime-core dissolution (deka#881). Artifact validation continues
to use the schema and fixture mechanism described here.

## 7. Open questions — recorded defaults

Two product commitments were left open in the draft. Phase 1 records the
conservative option for each so the spec is implementable end-to-end; both were
posted back to deka#761 for Sami's confirmation, and either can be revisited
without touching the layout or the verification order.

### 7.1 Signing and the trust root — recorded: digest-only for phase 1

Options were (a) ship digest-only, defer signing until artifacts cross a trust
boundary, and (b) sign now with minisign against the trust-root keys, adding key
custody and rotation to the deploy path.

**Recorded: (a).** An unsigned anchor is honest about what it catches (§3.1); an
unrotatable signing key in CI is worse than no signature. `build-manifest.sig` and
the filename are reserved by §3.3, and the follow-up is filed before per-shop
Worker deploys go multi-machine — at that point an artifact built on one machine
runs on infrastructure another party controls, which is the trust boundary that
justifies signing.

### 7.2 `runtime_abi` bump policy — recorded: exact match, deka version informational

Options were (a) gate on exact `runtime_abi` equality, with `producer.deka`
informational, and (b) gate on the deka minor version, invalidating every deployed
artifact on every minor release.

**Recorded: (a).** (b) means a compiler bump forces a rebuild-and-redeploy of
every shop, which is the operational cost RFD 54 exists to remove. This is a
product commitment about how long a built artifact stays servable: an artifact
built by deka 0.46 keeps serving on any deka that implements `runtime_abi 1`,
until the host-module contract itself changes.

## 8. What each downstream phase owes this spec

- **#762** — emit `dist/server/` per §1 and §4; `.values/` replaces `deka:dev/*`;
  drop the root-`index.html` requirement from `ensure_web_project_layout` and emit
  `client/index.html` as a build output; write `build-manifest.json` **into
  `dist/`** with its sidecar; exclude the three descriptor files from `payloads`.
- **#763** — artifact-only loader: §5.1 resolution, §5.2 classification, §3.4
  order, §4's resolution jail; delete the cache-first `deka:dev` fallback;
  re-root the Worker adapter on `dist/server`; build the §6 shape fixture.
- **#764** — the gate: serve with source, `.cache` and dsc removed; mutate source
  after build and prove served bytes are unchanged; each of the four §5.2 states
  produces its own diagnostic; tamper → connection refused, not 500; `deka dev`
  still watches and recompiles.
