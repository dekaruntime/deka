# Native runtime preview

Deka's native runtime compiles DekaScript to VM bytecode and renders a node tree
through its Rust layout, text and animation implementation. The compiler,
intermediate UI model, renderer and VM live together in Deka's repository.

This path does not require a JavaScript engine or WebView. Host operations expose
Rust capabilities to source code; the renderer handles layout and drawing. The
supported language and host surface is still a preview, not a claim of full
compatibility with the older JavaScript backend.

The runtime is tested with source compilation, execution and UI-event tests in
its owning crates, plus a relocated packaged-app test. The retired external
conformance corpus is no longer a release dependency.

Application testing remains a first-class feature: `deka test` runs DekaScript
tests for your application. Its current CLI implementation still uses the older
runtime while the VM integration is being completed. For npm installations use
`npx deka test` or your project's test script.

## Browser showcase

`deka_native_web` builds the local compiler, VM and Rust renderer into one WASM
module. The tour passes edited DekaScript to that module and uploads its scene
and glyph pixels to WebGL. It does not emit JavaScript components or style the
application through browser HTML/CSS.

A component entry named `App` returns a `view`. A `let` binding holds local state;
inline handlers assign to it. Dynamic text, classes, mapped children and
conditional children use the same component adapter as desktop. A conditional
executes only its selected branch. `None` contributes no child.

```tsx
export fn App() {
    let open = 0;
    return (
        <view className="p-4 gap-3">
            <button onClick={fn() { open = 1 - open; }}>Toggle</button>
            {open == 1 ? <p className="enter-fade exit-fade duration-500">Hello</p> : None}
        </view>
    );
}
```

Clicking Toggle shows and hides Hello. The VM evaluates bindings after events;
Rust advances the animation between events without executing more VM code.
Node identity is positional in this preview; keyed list reconciliation is not
implemented. Successful source edits restart state. Compilation or initial
render errors keep the last working application.

Browser text editing, asynchronous UI event scheduling, app module loading and
accessibility semantics are still integration work. Native host-specific input
and worker callbacks do not imply those features are available in the browser.

## Reusable component tags

A component is a function returning a view. Use an uppercase tag to compose it,
and pass named attributes through a checked props interface:

```tsx
interface CardProps { title: string; detail: string }

fn Card(props: CardProps) {
    return (
        <div className="p-4 gap-2">
            <p>{props.title}</p>
            <p>{props.detail}</p>
        </div>
    );
}

export fn App() {
    return (
        <view>
            <Card title="Deka" detail="A component is a function that returns a view." />
        </view>
    );
}
```

This displays the title and detail in the reusable card. Attribute order does
not matter. The checker reports missing, unknown and wrongly typed props before
execution. Parameterless components also work as tags. Relative file imports
can provide components in native apps; the browser tour still accepts one source file.
A prop can carry any value, including struct values, enum cases and interface
values, and a struct type can serve as the props type in place of an interface.

Nested markup supplies child content. Prefer `<slot />` to project it, including
when no content is supplied. To read `props.children` explicitly, declare its type
in the props interface. The existing `ReactNode` type describes renderable values;
no React runtime is involved. A bare boolean attribute means `true`.

Components in static markup are created once. Local `let` state and event
closures survive parent updates. Prop expressions are read when the component
uses them, so a child can display current parent state without being recreated.
Keep those expressions free of side effects. Values copied from props into a
local binding during creation are snapshots, not automatic derived bindings.
Dynamic conditional or mapped child creation still follows the preview's
existing positional identity behavior; this is not keyed reconciliation.

### Projecting children with a default slot

Place `<slot />` inside a component's view to display its nested markup:

```tsx
interface CardProps { title: string; detail: string }
fn Hero() { return <p>Testing</p>; }
fn Card(props: CardProps) {
    return (
        <div className="p-4 gap-3">
            <p>{props.title}</p>
            <p>{props.detail}</p>
            <slot />
        </div>
    );
}
export fn App() {
    return (
        <view>
            <Card title="Empty" detail="No nested content" />
            <Card title="Project" detail="Nested content follows">
                <Hero />
            </Card>
        </view>
    );
}
```

The second card shows Testing after its detail. The first slot contributes no
nodes. A default slot does not require a `children` declaration, a props
parameter, or pattern matching. It preserves child state and adds no layout
wrapper. An explicit optional `children?: ReactNode` declaration is also allowed;
`<slot />` handles its absence. Direct `{props.children}` still obeys the ordinary
optional-value type rule. Named slots and fallback content are not supported yet.
`<children />` is not an alias for `<slot />`.

## Struct embedding

Embedding a struct promotes its fields and methods. You can supply the embedded
value or initialize its fields directly; defaults and empty embeds are filled
when the value is created. Supplied initializers run once, in written order.

```tsx
struct Position { x: number; y: number = 2; }
struct Player { Position; }
let player = Player { x: 3 };
player.x = player.x + player.y;
// player.x is 5. A shared Position supplied explicitly sees promoted writes too.
```

Own fields take precedence over embedded fields. Writes through `let` update the
original embedded value, including aliases. Writes through `const` remain a
compile error. Arbitrary nested object fields are not promoted.

## Printing structs

`string(value)` formats a printable struct using its declared name and supplied
field order. Attached methods are omitted. Strings inside fields are quoted;
nested structs and lists keep their structure. `console.log(...)` and
`echo(string(value))` use the same Rust formatter.

```tsx
import { echo } from "io";
struct Point { x: number; y: number; }
const p = Point { x: 1, y: 2 };
echo(string(p)); // Point { x: 1, y: 2 }
```

`echo` still takes text, as before. This does not make arbitrary object-to-string
casts or string-plus-struct concatenation legal. Cyclic or deeply nested output
uses bounded placeholders rather than recursing indefinitely.

## Runtime types and declared signatures

`.getType()` returns an immutable, interned `Type` value describing the current
runtime value. `.signature()` describes the type declared at that source site.
Use `.toString()` to display either descriptor; equality compares interned type
identity. This slice exposes `toString()`, not schema-field introspection.

```tsx
let value: number | string = "hello";
value.getType().toString(); // string
value = 42;
value.getType().toString(); // number
value.signature().toString(); // number | string
```

Structs, enums and newtypes retain their names. Arrays report `Array` at runtime;
their static signature can describe the element type. Newtype construction and
arithmetic retain the checked result type, while unboxing returns the plain
primitive. User-defined `getType` and `signature` methods keep precedence over
the builtins. Descriptors survive collection while the VM runs and are released
when it finishes or is cancelled. No JavaScript helper is involved.

## Option and Result values

`Option` and `Result` are prelude enums. Namespace and short constructors create
real enum values through the same VM operation as declared enums:

```tsx
const present: Option<number> = Option.Some(7); // or Some(7)
const absent: Option<number> = Option.None;    // or None
const success: Result<number, string> = Result.Ok(1); // or Ok(1)
const failure: Result<number, string> = Result.Err("boom"); // or Err("boom")
console.log(present, absent, success, failure);
// Some(7) None Ok(1) Err("boom")
```

`string(value)` and `console.log(value)` share the enum formatter. Use
`echo(string(value))` for the text-only `echo` operation. Nested enums retain
their cases (`Some(Ok(7))`); string payloads are quoted and escaped. Declared
variants follow the same rule (`Circle(5)`, `Empty`). Objects with fields named
`name`, `index` or `value` keep object formatting; they do not become enums.
`None` also remains an empty child in a view. Constructors and printing do not
change the rules for string concatenation or widen the host wire types.

The native VM retains `Some` as a value, rather than erasing it to its payload
as the former JavaScript backend did.

## Matching values

`match` is an expression: it evaluates its subject once, selects an arm, and
returns that arm's value. Enum patterns extract payloads; nested patterns can
inspect their cases or scalar values. A failed nested pattern continues to the
next arm before reading any deeper payload.

```tsx
fn label(value: Option<Result<number, string>>) string {
    return match (value) {
        Some(Ok(7)) => "seven",
        Some(Ok(n)) => "number: " + string(n),
        Some(Err(message)) => message,
        None => "empty",
    };
}
// label(Some(Ok(8))) is "number: 8".
```

Numbers, strings and booleans support literal arms with a default (`_`), or a
catch-all binding. Declared enums support qualified or unqualified case names;
a payload-free case name tests that case rather than binding a variable.
`Red | Green` groups alternatives under one arm. Tuple and struct patterns can
extract nested fields. Arm bindings are local to their arm; closures retain
captured bindings when a surrounding loop moves to its next iteration.

The existing checker still rejects non-exhaustive matches with the missing
cases in the diagnostic. Native type patterns for scalar, struct and enum union
members use their actual runtime type or nominal brand. A failed case predicate
is false, including when the runtime value has another kind. Bytes and host
error class patterns require their corresponding host value support.

## Unwrapping with a fallback

An unwrap binding extracts the payload of `Some` or `Ok`. Its `or` alternative
runs only for `None` or `Err`. The subject is evaluated once.

```tsx
fn label(value: Option<string>) string {
    const text = unwrap(value) or { return "unavailable"; }
    return "got: " + text;
}
// label(Some("yes")) is "got: yes"; label(None) is "unavailable".
```

A trailing expression in `or { ... }` supplies the binding's value. Otherwise,
the block must leave the enclosing function on every path. A `return` stays in
that function; the fallback does not create a separate closure. The checker
rejects empty alternatives and incompatible fallback types. Local names in the
alternative stay local, and `const`/`let` retain their normal mutation rules.

For a Result, `or match` can use the error payload:

```tsx
fn label(value: Result<string, string>) string {
    const text = unwrap(value) or match { Err(e) => "failed: " + e };
    return text;
}
```

The implicit success arm supplies the `Ok` payload. The checker requires the
remaining failure cases to be covered. For Option, use `or { ... }`; there is no
error payload for `or match` to inspect. Module-level unwrap bindings execute in
source order and are available to functions like other bindings. Existing
`safe { expression }` wrappers preserve the expression, and logical `||` keeps
its normal short-circuit behavior; neither substitutes for unwrap or match.


## Checked exceptions

`Exception<T, E>` describes a function’s success and escaping failure channels.
It is control flow: `Ok(value)` returns the success payload, and `Throw(error)`
unwinds to the nearest active handler. It cannot be saved as ordinary data.
Consume an Exception call where you call it, with `match`, inside `try`, or by
an exact-channel return to the caller. Use `Result` when failure should be data.

```tsx
fn read(fail: boolean) Exception<number, string> {
    if (fail) { return Throw("unavailable"); }
    return Ok(7);
}
fn label(fail: boolean) string {
    return match read(fail) { Ok(value) => string(value), Throw(error) => error };
}
// label(false) is "7"; label(true) is "unavailable".
```

`try { ... } catch (error) { ... }` handles throws raised in its body or by calls
inside it. A typed catch for a struct handles only that declaration, including
when imported under an alias. Other thrown types propagate to the next handler.
Catch bindings stay local. Throws raised by match arms and catch bodies propagate
outward; they are not caught again by their own handler. A bodyless `Throw(e)`
arm forwards the original payload.

`read(true).to_result()` explicitly converts a thrown error into `Err(error)`;
a success becomes `Ok(value)`. `Exception.from(result)` performs the reverse
conversion. Neither evaluates its subject more than once. Nested and wildcard
bodyless arms keep the original payload when forwarding Result or Exception.

The VM retains handler state across suspension. An async function’s language
Throw reaches the caller at `await` and uses the same match or catch handling.
VM faults such as `panic` remain runtime errors and do not enter catch blocks.
An uncaught Throw prints its payload on stderr and exits unsuccessfully. Native
host error class constructors require the host value support; struct catches do
not depend on a JavaScript engine.

Imported struct literals can supply fields explicitly. Omitting a field whose
value needs an imported default currently produces a named compile error;
its default must run in the declaring module, never in the importer’s scope.


## Awaited host failures

A fallible native host operation exposes `Result<T, string>` or, when async,
`Promise<Result<T, string>>`. Its successful reply becomes `Ok(value)` and an
operational error becomes `Err(error)`. An awaited Err is data: a `try` block
does not catch it. Handle it with match, unwrap or other Result operations.

```tsx
// For a registered read operation returning Promise<Result<string, string>>:
async fn label() Promise<string> {
    return match await read() { Ok(value) => value, Err(error) => "failed: " + error };
}
```

Native embedders opt into this contract with `HostOp::with_result_channel()`.
The same registry generates the source signature and dispatches both immediate
and pending replies. Existing infallible operations keep their plain output
contract. Invalid arguments, denied capabilities and a reply with the wrong
wire type remain VM faults; they are not operational Err values or language
Throw. This supplies the host I/O integration hook; it does not add a fetch
operation or a desktop async event loop by itself.

## Array reduction

`items.reduce(callback)` folds a nonempty array from left to right. The first
item is the initial accumulator; subsequent calls receive the accumulator and
the next item. A singleton array returns its item without invoking the callback.

```tsx
const total = [1, 2, 3].reduce(fn(acc: number, item: number) number {
    return acc + item;
}); // 6
```

The receiver and callback are evaluated once. Traversal captures the original
length, reads each element when visited and skips indices removed by callback
mutations. Items appended beyond that original length are not visited. Callback
faults propagate; reducing an empty array reports
`cannot reduce an empty array without an initial value`. The current signature
accepts one callback and no explicit initial value.
